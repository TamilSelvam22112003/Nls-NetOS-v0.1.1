# NLS v2 Cryptographic and Wire Golden-Vector Plan

- Status: conformance plan; one positive fixed-width Router-CA status vector and verifier are committed. The fixed-width status signature was independently verified with OpenSSL after generation using Python cryptography; parser/policy negative vectors and destination-handshake vectors remain open.
- Scope: shared conformance fixtures consumed by NexOS Core and NetOS.
- Rule: expected bytes and cryptographic outputs must be generated by a reviewed independent reference harness, checked into both repositories byte-for-byte, and verified by a second implementation. Never hand-invent expected cryptographic outputs.

## 1. Fixture format

Each vector fixture must record:
- vector identifier and protocol-draft revision/hash;
- deterministic test-only inputs (private keys, nonces, cookie secret, endpoints, ports, IDs, time bucket, certificate/status test objects);
- expected encoded bytes as lowercase hex, with no omitted fields;
- expected intermediate values (canonical signed bytes, signature, X25519 shared secret, transcript hash, HKDF salt/info/output, nonce, AAD, ciphertext and tag);
- expected result: accept/reject and a stable error category;
- provenance: generator version, library versions, and independent verification record.

All keys and identities in fixtures must be synthetic test material, never production secrets. Include a warning in each fixture directory that the keys are test-only.

## 2. Encoding vectors

Generate positive and negative vectors for:
1. 44-byte common header: DATA, CONTROL, all defined fields, big-endian integers, reserved bits/bytes, exact payload length.
2. Control prefix and TLV stream: strict ascending full 16-bit type order; length prefixes; zero-length behavior; duplicate, reordered, truncated, unknown-critical and trailing bytes.
3. INIT without cookie, RETRY cookie, INIT with cookie, RESP, FINISH_I, FINISH_R, CLOSE, and rejection of reserved KEY_UPDATE.
4. Payload lengths: plaintext INIT/RETRY/RESP count control-payload bytes; AEAD-protected FINISH_I/FINISH_R and established controls/DATA count ciphertext plus the 16-byte tag.
5. Maximum configured datagram, one byte over limit, arithmetic-overflow attempts, and truncation at every field boundary.

## 3. Cookie vectors

Fix test-only values for source/destination IPv6 addresses, UDP ports, handshake_id, nonce_i, ephemeral_x25519_i, time bucket, and HMAC secret. Publish:
- exact cookie MAC input bytes;
- expected HMAC-SHA-256 output and 40-byte cookie;
- acceptance for current and immediately previous time bucket;
- rejection for expired/future buckets, changed source/destination/port, changed handshake_id/nonce/ephemeral key, and rotated-out secret;
- amplification-size accounting for INIT and RETRY.

## 4. Signature and transcript vectors

For RESP and FINISH_I, publish:
- exact canonical signature input bytes;
- canonical control payload with signature TLV omitted;
- exact endpoint tuple ordering and role;
- Ed25519 public key and expected 64-byte signature;
- verification result for a one-bit change in each bound field.

For transcript/key derivation, publish:
- exact encoded INIT-with-cookie and RESP datagrams used as transcript inputs;
- T0 SHA-256 output;
- salt input bytes and salt hash;
- X25519 public keys and shared secret;
- exact HKDF info labels and each 32-byte directional handshake/data key;
- expected rejection of an all-zero shared secret and altered transcript.

## 5. AEAD vectors

For FINISH_I, FINISH_R, CLOSE, and DATA, publish:
- exact 44-byte header;
- outer source/destination IPv6 addresses and UDP ports;
- exact AAD concatenation bytes;
- directional key, key_epoch, sequence_number and 12-byte nonce;
- plaintext bytes, ciphertext bytes, 16-byte tag, and complete datagram;
- tamper tests for header, endpoint tuple, ciphertext, tag, direction, session token, epoch and sequence number.

FINISH_I and FINISH_R use separate directional handshake keys and nonce `uint32_be(0) || uint64_be(0)`; retransmission must repeat identical datagram bytes, never encrypt different plaintext under that same key/nonce. DATA uses the session's directional data key and nonce `uint32_be(key_epoch) || uint64_be(sequence_number)`.

## 6. State-machine and adversarial vectors

Cover:
- out-of-order, duplicate, replayed, and cross-session messages;
- same-identity concurrent handshakes;
- invalid certificate chain, identity fingerprint, endpoint binding, status signature/freshness/generation, revocation and CA outage;
- unsupported suite, attempted downgrade, invalid cookie and cookie replay;
- duplicate FINISH retransmission and bounded-cache expiry;
- session expiry, process restart, sequence persistence uncertainty, and key erasure;
- replay-window edges, reordering, sequence wrap, and wrong-direction keys;
- invalid lengths, resource caps, rate-limit and anti-amplification behavior.

## 7. Acceptance requirements

- Core and NetOS must consume the same committed fixtures without editing expected values.
- Every vector has at least one positive and one negative assertion where applicable.
- A second independent implementation or reviewer verifies cryptographic intermediate values.
- Property-based and fuzz tests complement vectors; they do not replace them.
- CI fails on fixture drift, missing vectors, or different serialization/output.
- No claim of interoperability until all mandatory vectors pass in both repositories and a multi-router lab validates actual packet handling.
